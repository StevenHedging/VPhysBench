# Physics Video Benchmark 数据集说明与使用手册

## 1. 这份手册解决什么问题

这是 `datasets/` 的唯一权威说明，也是向 Benchmark 接入新数据时必须先读的使用手册。
它面向 AI 助手和真人，回答两类问题：

1. 当前数据集由什么组成，Scene 和原子 Case 分别表示什么；
2. 当一个新 Scene 只提供原始视频和粗糙 XLSX 标注表时，怎样把它整理成可训练、可评测、
   可追溯的数据。

## Hugging Face 私有同步仓库

当前 Git 仓库通过 [`huggingface.json`](huggingface.json) 绑定私有 Hugging Face Dataset
`StevenHedging/VPhysBench`。绑定固定到不可变 Hub commit，并同时校验 Dataset ID 与
release；访问凭证只保存在用户级 Hugging Face credential cache，不能写入仓库文件。

当前远端已同步 Dataset 13.0.0 的轻量 release 索引，媒体资产仍待单独上传。已获授权的
协作者可按绑定 revision 下载到本地 `datasets/`：

```bash
hf download StevenHedging/VPhysBench \
  --repo-type dataset \
  --revision 04ef16102216a3231f045152ab3a996f5f353f63 \
  --local-dir datasets
```

数据导入的核心不是“把文件复制进目录”，而是可靠地建立以下关系：

```text
一个有效 Case
= 一个明确的物理试次
+ 一段边界正确的参考视频及其第 0 帧
+ 一份可理解、可归一化的结构化物理信息
+ 一条无数值泄露且语义完整的过程描述
+ 每个物理主体在首帧中的独立 mask
+ 可追溯的视频—XLSX 对应与处理记录
```

如果视频和物理标注无法可靠对应、关键字段无法理解，或者视频不包含完整有效的物理过程，
不得猜测补全。应暂停该条 Case、向用户说明问题，并将它列入排除清单。

## 2. 当前数据集的构成

### 2.1 Scene

Scene 是一种物理过程及其数据契约。它定义主体是什么、过程从哪里开始和结束、哪些量属于
正式物理标注、Caption 应如何描述、哪些主体需要 mask，以及后续采用什么评估逻辑。

当前共有 7 个 Scene、916 条 Case：

| Scene ID | 物理过程 | Case 数 | 当前正式物理量概览 |
| --- | --- | ---: | --- |
| `pendulum` | 单摆 | 100 | 摆球质量、半径、初始角；绳长 |
| `collision_1d` | 一维对心碰撞 | 330 | 各球质量、半径、初始速度大小 |
| `inclined_plane_slide` | 斜面下滑 | 95 | 物块质量、长度；斜面倾角、重力加速度 |
| `uniform_circular_motion` | 匀速圆周运动 | 36 | 各主体轨道半径；角速度 |
| `parabolic_motion` | 平抛运动 | 97 | 球质量、半径、初始水平速度大小、发射高度 |
| `push_bottle` | 推水瓶 | 141 | 瓶子质量、高度、完整外力时间序列 |
| `vertical_spring_oscillator` | 竖直弹簧振子 | 117 | 振子质量、球半径、初始位移；重力加速度、弹簧原长与劲度系数 |

每个 Scene 的有效 Case 会被划分为训练集和较小的 ID 测试集，不再构造 OOD 测试集。
通常每个 Scene 的测试 Case 不超过 20 条；同一原始试次、重复视频或高度近似的重复组不得
跨训练集和测试集。

### 2.2 对数据导入者有意义的目录

```text
datasets/
├── assets/
│   └── <scene_id>/
│       └── <case_directory>/
│           ├── caption.json
│           ├── physics.json
│           ├── source/                 # 可选：该 Case 的原始媒体副本
│           └── canonical/
│               ├── reference.mp4|mov
│               ├── first_frame.png
│               └── masks/
│                   ├── 01.png
│                   ├── 01.npz
│                   ├── 02.png          # 多主体时继续编号
│                   ├── 02.npz
│                   └── manifest.json
└── provenance/
    ├── source_archives/                # 收到的原始压缩包
    ├── source_docs/                    # 原始 XLSX 等说明材料
    └── imports/                        # 映射、排除、清洗和复核记录
```

`assets/` 保存可直接被 Dataset 使用的 Case 资产；`provenance/` 保存来源事实和导入证据，
不作为模型的结构化物理输入。运行索引、Scene 元数据和训练/测试划分只引用 Case，不重复
保存 `caption.json` 或 `physics.json` 的正文。

Case 目录名应简短、可读，包含主要结构化物理量的归一化值和唯一来源后缀。目录名不能编码
背景、颜色、机位等非物理信息。稳定身份由 `case_id` 决定，目录路径不是身份。

### 2.3 什么是原子 Case

原子 Case 表示一次不可再拆分的真实物理试次。它的四类核心成员是：

1. **视频成员**：`canonical/reference.*` 及从其第 0 帧直接解码得到的
   `canonical/first_frame.png`；
2. **结构化物理信息**：Case-local 的 `physics.json`；
3. **文本描述**：Case-local 的 `caption.json`；
4. **主体 mask**：`canonical/masks/` 中与 `object_N` 一一对应的首帧实例 mask。

这四者必须描述同一次试次，并共享相同的 `case_id` 和 `scene_id`。Baseline 的缩放、补边、
抽帧、特征、模型输入缓存以及生成结果都不是 Case 成员，不能写回 `datasets/`。

规范上的完整 Case 必须具有全部主体 mask。当前 916 条 Case 中有 914 条已具有 mask；以下
两条斜面 Case 尚缺 mask，属于待补齐项，不能作为新数据省略 mask 的先例：

- `incline_r1_a41deg_bgoil_img_0332`
- `incline_r1_a44deg_bgblack_img_0394`

## 3. 接入新 Scene 前必须确认的四个问题

在处理正式文件前，AI 助手必须向用户确认下面四项。用户已经明确回答过的内容，不要机械
重复提问；应先复述已知结论，只询问仍有歧义或尚未覆盖的部分。

> 1. **视频窗口与画面**：目标物理过程从什么事件开始、到什么事件结束？是否需要时间剪辑
>    或空间裁剪？首帧中必须出现哪些主体、不得出现哪些人手或装置？
> 2. **XLSX 与正式物理量**：哪些字段属于各 `object_N` 的正式物理量，哪些属于
>    `environment`，哪些只用于来源、外观、实验形式、辅助测量或质量审核？每个字段的定义、
>    单位和方向语义是什么？
> 3. **Caption**：怎样无歧义地描述主体数量、初始状态、运动方向、相互作用顺序和完整物理
>    过程？该 Scene 为每个正式物理量使用哪些稳定 `symbol`？
> 4. **Mask 主体**：哪些可见实体是需要编号和 mask 的物理主体，哪些只是装置或环境？
>    主体在首帧中的编号如何确定，是否存在遮挡、进出画面或首帧不可见的情况？

确认结果共同构成该 Scene 的数据契约。不要先批量生成 Case，再根据结果反推这四项规则。

## 4. 问题一：原始视频是否需要剪辑

### 4.1 先定义物理事件，而不是先找固定帧号

每个 Scene 必须先用可观察事件定义：

- **起点事件**：什么瞬间应当成为 canonical 视频第 0 帧；
- **终点事件**：到什么瞬间才算包含完整的待评物理过程；
- **首帧可见性**：哪些主体必须完整出现在画面中；
- **排除内容**：人手、光电门、线缆或其他装置是否必须离开画面；
- **运动区域**：空间裁剪后是否仍能容纳主体的完整轨迹。

例如，“球刚穿过光电门的瞬间”是事件定义；“从第 37 帧开始”只是某个视频对该事件的
具体定位。批量数据必须逐条定位事件，不能假设所有视频使用同一个帧号。

### 4.2 何时不剪、何时剪

如果原始视频第 0 帧已经对应约定起点，画面干净、全部主体完整可见，而且结尾包含完整过程，
应保留原视频，不做无意义转码。

只在以下情况下进行必要处理：

- 删除准备阶段、人手尚未离开或物理过程尚未开始的前缀；
- 删除与目标过程无关的尾部，但不能截断仍需评估的运动；
- 裁掉明确要求不得出现的光电门、人手或辅助装置；
- 调整裁剪框，使全部物理主体和完整运动区域保留在画面内。

空间处理不得通过补黑边、拉伸或非等比变形制造目标画幅。Dataset 不为某个模型修改视频
规格；模型画布适配属于 Baseline。

### 4.3 时间与首帧规则

- 保留所选物理时间窗口内的原始 FPS 和全部原始帧；
- 不抽帧、不插帧、不重采样 FPS、不改变播放速度；
- 不为满足模型的固定时长而延长、循环或截短物理过程；
- `first_frame.png` 总是从最终 `reference.*` 的第 0 帧直接解码；
- 不允许从另一帧、原视频或单独照片复制一个“近似首帧”；
- 如需时间剪辑，必须记录源起止帧或时间点；如需裁剪，必须记录裁剪框和理由。

### 4.4 视频验收

每条视频至少检查首帧、中间运动和尾部：

- 第 0 帧确实是用户确认的起点事件；
- 首帧中所有需要编号的物理主体完整可见；
- 不应出现的人手和装置已被去除；
- 裁剪没有切掉主体或后续轨迹；
- 视频没有过早结束，物理过程与 Caption 一致；
- `first_frame.png` 与 `reference.*` 第 0 帧解码结果一致。

依赖精确起点的 Scene 应逐条检查，不能用少量抽样替代。

## 5. 问题二：怎样把粗糙 XLSX 整理为 `physics.json`

### 5.1 先理解表格，再写 JSON

先只读盘点 XLSX 的 sheet、表头、单位、合并单元格、公式、空行、备注和视频定位字段，
然后建立字段决策表。不得直接把整行表格机械转换成 `physics.json`。

| XLSX 字段类别 | 例子 | 去向 |
| --- | --- | --- |
| 主体正式物理量 | 质量、半径、长宽高、初始速度、作用于该主体的外力序列 | `physics.objects.object_N` |
| 环境正式物理量 | 重力加速度、斜面倾角、绳长、系统角速度 | `physics.environment` |
| 派生或辅助量 | 均值、峰值、遮光时间、校准读数、重复别名 | provenance，不进入 `physics` |
| 情景和外观信息 | 背景、颜色、材质标签、视角、球数、实验形式 | 非物理元数据；必要时用于分层，不进入 `physics` |
| 来源和质量信息 | 视频名、行号、操作者、备注、异常说明 | provenance 和排除审核 |

如果一个字段完全无法理解，必须向用户询问，不能根据列名或相邻行猜测。如果视频找不到
唯一对应的物理标注，则舍弃该视频并报告；不能仅按文件名排序和表格行序配对。

### 5.2 `objects` 和 `environment` 的边界

`physics.objects.object_N` 保存属于第 N 个物理主体的正式参数：

- 固有属性：质量、半径、长度、宽度、高度等；
- 初始动力学状态：初始速度大小、初始角度等；
- 明确作用于该主体且需完整保留的输入信号，例如 `applied_force` 的时间序列。

`physics.environment` 保存作用于整个过程、约束系统运动或定义主体所处物理条件的正式参数，
例如重力加速度、斜面倾角、绳长和系统角速度。定义在主体与环境或多个主体之间的正式相互
作用参数，也放在 `environment`，字段名必须明确表达它所描述的界面或对象关系。

判断标准是“这个量在物理模型中归属于谁”，而不是“它在 XLSX 的哪一列”。
`environment` 可以是空对象。背景、颜色、机位、实验形式、装置规格和审核信息无论多么有助于
区分试次，都不是正式物理参数，不能进入这里。

### 5.3 `physics.json` 的固定结构

完整文件只保存 Case 身份和正式物理量：

```json
{
  "case_id": "<stable_case_id>",
  "scene_id": "<scene_id>",
  "physics": {
    "objects": {
      "object_1": {
        "mass": {
          "value": 0.03313,
          "unit": "kg",
          "symbol": "m_1"
        }
      }
    },
    "environment": {
      "gravity_acceleration": {
        "value": 9.80665,
        "unit": "m/s^2",
        "symbol": "g"
      }
    }
  }
}
```

每个标量只能包含：

```json
{
  "value": 0.03313,
  "unit": "kg",
  "symbol": "m_1"
}
```

每个时序量只能包含：

```json
{
  "samples": [
    {"time": 0.1, "value": 0.16},
    {"time": 0.2, "value": 0.27}
  ],
  "time_unit": "s",
  "unit": "N",
  "symbol": "F(t)"
}
```

### 5.4 量值、单位、方向和符号规则

- 优先归一化到 SI 单位，并在 provenance 中保留原字段、原值和换算依据；
- 无量纲量的 `unit` 使用 `"1"`；
- 正式数值必须有限且非负，只表达物理量大小；
- 运动方向、旋转方向和力的方向写进 Caption，不用负号或画面坐标暗示；
- 缺失值不能用 `0` 填充；必需量缺失时排除该 Case，可选量缺失时按 Scene 契约省略；
- 每个正式量必须有非空 `symbol`，同一 Case 内不能重复；
- 同一 Scene 的同类量使用稳定符号，多主体量用下标与 `object_N` 对齐；
- Caption 必须逐字包含 `physics.json` 中的每个 `symbol`；
- 时间序列保留 XLSX 中显式时间戳和原始顺序，不插值、不平滑、不去重、不重采样；
- 均值、峰值等可从完整信号推导的摘要不与原时序量并列作为正式输入。

## 6. 问题三：怎样编写 `caption.json`

### 6.1 Caption 的目标

Caption 要简洁、无歧义地描述可见物理过程。理想效果是：生成模型只看首帧和 Caption，
就能理解应当生成什么过程；结构化物理信息再提供精确数值。

当前 Caption 使用英文。文件结构为：

```json
{
  "case_id": "<stable_case_id>",
  "scene_id": "<scene_id>",
  "caption": "A block of mass m and length l starts from rest and slides down an incline of angle θ under gravitational acceleration g."
}
```

### 6.2 必须写什么

- `physics.json` 中每个正式量的 `symbol`，且拼写完全一致；
- 物理主体数量和角色；
- 初始静止或运动状态；
- 必要的运动方向、旋转方向；
- 多主体的初始运动关系和相互作用顺序；
- 结果过程，例如碰撞、摆动、下滑、平抛、倾倒。

### 6.3 不能写什么

- 任何具体物理数值或单位；符号下标中的数字不属于数值泄露；
- 背景、颜色、材质外观、拍摄视角、相机、分辨率和裁剪信息；
- 人手、光电门、线缆以及采集装置；
- 文件名、批次、Case ID 或质量审核提示；
- 从结果视频事后总结出的轨迹数值或得分提示；
- 模糊到无法确定主体、方向或过程的泛化模板。

不要把所有同 Scene Case 强行套入一句模板。碰撞等结构多样的 Scene 必须按每条 Case 的
主体数量、初态与交互关系精确描述，但仍不能写具体数值。

### 6.4 编写与检查顺序

1. 从 `physics.json` 收集全部 `symbol`；
2. 从用户确认的 Scene 契约和非物理实验形式中确定主体数量、角色和过程；
3. 写一到两句英文 Caption；
4. 检查全部符号均出现且没有额外数值、单位或采集提示；
5. 对照首帧和完整视频检查主体、方向、初态与过程是否一致。

## 7. 问题四：哪些物理主体需要 mask

### 7.1 主体定义

需要 mask 的物理主体，是该 Scene 中被独立编号、具有对象物理属性或需要独立追踪的动态
实体。每个 `physics.objects.object_N` 必须恰好对应一个首帧主体 mask。

以下内容默认不作为主体：背景、桌面、斜面、支架、固定转轴、导轨、光电门、人手、线缆和
仅用于实验实现的辅助装置。如果某个实体在新 Scene 中确实是待评物理过程的一部分，必须在
四问确认阶段明确把它定义为主体，不能因为“画面中可见”就自动加 mask。

例如，画面中有五个需独立追踪的球，就应有 `object_1` 至 `object_5` 和五组 mask 文件；
斜面上的单个物块通常只有 `object_1`，斜面参数属于 `environment`，斜面本身不因此成为
`object_2`。

### 7.2 编号规则

编号以 canonical 首帧为准，按矩阵索引顺序：先从上到下确定行，同一行内从左到右编号。
结果必须同时用于：

- `physics.objects.object_1`、`object_2`……；
- `canonical/masks/01.*`、`02.*`……；
- `manifest.json` 中的 `object_id`；
- Caption 中多主体角色和方向的语义核对。

如果主体严重遮挡、首帧不全或初始时在画外，默认不能生成可靠原子 Case。应先调整视频起点
或裁剪策略；仍无法满足时必须向用户报告，由用户重新定义 Scene 契约或排除该视频。

### 7.3 Mask 文件要求

- 当前 mask 只表示 `first_frame.png` 上的可见主体像素；
- 每个主体保存一个全分辨率二值 PNG 和一个供程序读取的 NPZ；
- `01` 对应 `object_1`，编号不能按文件名、XLSX 行序或运动先后重新排列；
- PNG 与 NPZ 的空间尺寸必须等于首帧尺寸；
- mask 只包含该主体，不包含阴影、支架、接触面或相邻主体；
- `manifest.json` 记录 Case、首帧、主体编号、mask 路径以及对应的物理字段；
- 自动分割结果必须逐条视觉复核，不能只依据模型置信度通过。

## 8. 从原始 Scene 到正式 Case 的完整流程

### 第 0 步：只读盘点

在修改正式资产前记录：

- 压缩包和目录中的全部成员；
- XLSX 的 sheet、表头、单位、公式、合并单元格和非空行；
- 每个视频的文件名、容器、编码、宽高、FPS、帧数、时长和旋转信息；
- 当前同 Scene 的既有 Case、目录命名、物理字段、符号和 Caption 风格。

原始压缩包和 XLSX 放入 provenance 对应位置。只保留来源事实和处理记录，不生成哈希、
资产锁或其他与数据内容无关的安全文件。

### 第 1 步：建立视频—标注确定映射

优先使用视频文件名、实验编号、时间戳或表内明确主键建立一一对应。输出逐条映射表并检查：

- 一条视频不能未经说明对应多行互相冲突的标注；
- 一行标注不能误配给多个不同试次；
- 不能仅依赖自然排序或“最接近的一行”；
- 没有标注的视频排除并报告；
- 没有视频的 XLSX 行忽略并计数；
- 与既有 Case 或本批次重复的媒体和试次排除并报告。

### 第 2 步：形成字段决策草案

逐列列出原字段、示例值、物理含义、单位、目标类别、目标键、换算方式和疑问。特别区分：

- 正式独立物理量；
- 可由正式量推导的摘要；
- 仅用于校准或复核的辅助量；
- 背景、外观、实验形式和采集信息；
- 文件定位与质量备注。

### 第 3 步：完成四问确认

把已知结论和仍有疑问的内容整理成第 3 节的四个问题，请用户一次性确认。用户已明确提供的
答案应直接纳入总结。任何无法理解且会改变物理标注、视频窗口、Caption 或主体定义的问题，
必须在批处理前解决。

### 第 4 步：建立 Scene 契约

记录并固定：

- `scene_id`、中文名称和物理过程边界；
- canonical 起点、终点、首帧可见性与裁剪规则；
- 主体类别、数量范围、编号和 mask 规则；
- 正式物理字段、对象/环境归属、单位、符号、必需性和合法范围；
- Caption 必须表达的初态、方向和过程信息；
- 非物理元数据字段、重复判定标准和视觉验收标准。

### 第 5 步：先做少量试制 Case

选择能覆盖不同主体数量、视频规格和 XLSX 特殊情况的少量样例，完成视频、首帧、
`physics.json`、`caption.json` 和 mask。逐条核对四者一致后再批量处理，避免错误规则扩散。

### 第 6 步：批量生成并持续抽查

按确认后的规则生成描述性目录和稳定 `case_id`。批处理中持续检查：

- 视频首帧和过程边界；
- 单位换算与字段归类；
- `object_N`、物理字段和 mask 编号；
- Caption 的符号覆盖、方向和禁写内容；
- 文件路径、身份字段和视频—XLSX 映射。

高风险 Scene 和精确起点 Scene 需要逐条视觉检查；其他 Scene 也应采用高覆盖、分层抽查，
并对异常组全量检查。

### 第 7 步：同步 Dataset 的下游索引

资产通过验收后，使用仓库现有构建流程同步：

- Case 轻量索引及其中的资产引用、外观信息和物理时间比例；
- Scene 元数据中的正式物理字段、约束和评估需求；
- 训练集和 ID 测试集成员；
- 直接评测所需的完整 Case 分组；
- 使用该 Dataset 的 Task 和对应测试。

Case 的 Caption 和物理正文仍只保存在 Case-local 文件，索引只引用路径，不复制正文。

### 第 8 步：机器校验和最终视觉验收

至少运行项目当前的数据门禁：

```bash
make test
```

并针对本次接入检查：

- Case ID、路径和视频—标注映射唯一；
- 所有资产路径存在且未逃逸 `datasets/`；
- `first_frame.png` 与 reference 第 0 帧一致；
- 视频 FPS 与所选窗口内帧序列未被重采样；
- `physics.json` 只有 `objects`、`environment` 和合法 quantity；
- 所有值有限且非负，所有符号非空、唯一并出现在 Caption；
- 每个 `object_N` 恰有一个正确编号的 mask；
- Caption 无物理数值、单位、背景、颜色、视角和采集信息；
- 训练集和测试集互斥、完整、无重复泄漏，测试集处于训练支持域；
- 首帧、完整视频、Caption、physics 和 mask 在语义上逐条一致。

## 9. 必须暂停或排除的情况

以下情况不能靠猜测或默认值继续：

| 情况 | 处理 |
| --- | --- |
| 视频找不到唯一 XLSX 标注 | 排除视频并报告 `missing_annotation` 或映射歧义 |
| 标注有行但找不到视频 | 忽略该行并计数，不生成空 Case |
| 物理字段无法理解 | 暂停相关 Case，向用户询问 |
| 必需物理量缺失 | 排除，不能用 0 或均值填补 |
| 标注与视频主体或过程矛盾 | 暂停复核，无法解决则排除 |
| 与既有数据或本批次重复 | 保留一条权威试次，其余列入重复清单 |
| 起点、主体可见性或完整过程无法满足 | 调整必要剪辑；仍失败则排除 |
| mask 无法和 `object_N` 可靠对应 | 暂停，不生成错误绑定 |
| Caption 需要靠具体数值才能消除歧义 | 重写过程语义或向用户确认，不写数值 |

排除不等于静默丢弃。最终报告必须列出原始定位、数量和具体原因。

## 10. 最终交付与验收清单

导入完成后，执行者必须在当前页面向用户报告：

- [ ] 收到的视频数、XLSX 有效行数及成功一一对应数；
- [ ] 导入、排除、忽略和重复的数量及逐条清单；
- [ ] 四个基本问题的最终答案和 Scene 契约摘要；
- [ ] 每个 XLSX 字段的分类、单位换算和符号；
- [ ] 视频是否剪辑、每条异常处理及视觉复核覆盖率；
- [ ] Caption、physics、mask 和视频的一致性检查结果；
- [ ] 新增训练 Case 和 ID 测试 Case 数量；
- [ ] 机器校验结果及仍未解决的风险。

只要仍有无法理解的正式物理标注或无法确定的视频—标注对应关系，任务状态就只能是
“部分完成，等待澄清”，不能把推测包装成完成结果。

## 11. 给未来 AI 助手的可复制开场模板

```text
我已经阅读 datasets/README.md。在处理正式文件前，我会先盘点视频和 XLSX，并请你确认
这个 Scene 的四项数据契约：

1. 视频的目标物理过程从什么事件开始、到什么事件结束？是否需要时间剪辑或空间裁剪？
   首帧中必须出现和不得出现什么？
2. XLSX 中哪些字段是每个 object 的正式物理量，哪些是 environment 的正式物理量，

   如何按从上到下、同一行从左到右确定？

少量样例进行视频、physics、caption 和 mask 的一致性检查，再批量导入；无法对应标注、
无法理解物理含义或与既有数据重复的条目会被排除并逐条报告。
```
